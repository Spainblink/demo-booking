## 2. Случай, где ИИ ошибся или предложил неоптимальное решение (или что перепроверили)

1. **Policy вместо логики в сервисе.** ИИ сам завёл `BookingPolicy` + `Gate::authorize`, хотя в правилах/ТЗ этого не было — достаточно проверки автора в `BookingService`. Лишний слой без необходимости.
2. **Некорректный ответ при конкурентной блокировке комнаты.** После валидации в транзакции стоял `lockForUpdate()`; при уже залоченной строке путь сводился к «комната не найдена» / неочевидному ответу, хотя комната существует — клиенту нужен понятный 422 про занятость/повтор.
3. **Backed enum с одинаковыми значениями.** В `BookingRule: int` одновременно `MinDurationMinutes = 15` и `SlotMinutes = 15` — в PHP так нельзя; пришлось убрать backing и отдавать числа через `value()`.

Как заметили / как перепроверили (построчный review):

1. Открыл diff / список новых файлов → увидел `app/Policies/BookingPolicy.php`, которого не просил.
2. Сверил с ТЗ и своим правилом «бизнес-логика в сервисе, контроллер тонкий» → Policy не из требований.
3. В `destroy` контроллера нашёл `Gate::authorize` → лишняя связь с Policy.
4. В `BookingService::create` дошёл до блока `DB::transaction` → строка с `lockForUpdate` / `lock(...)`.
5. Мысленно прогнал сценарий: проверки ок → параллельный запрос держит lock на той же комнате → что вернём клиенту?
6. Увидел ветку «не нашли строку / не взяли lock» с текстом про «не найдена» → это ложный диагноз при живой комнате.
7. Открыл `BookingRule` → два case с одним int → вспомнил ограничение backed enum → воспроизвёл мысленно/по доке PHP.
8. После правок прогнал feature-тесты в Docker (в т.ч. lock-тест) и сверил статусы/тело 422.

## 3. Что проверили вручную и что сознательно не доверили ИИ

**Вручную:**

- Итоговую работоспособность API помимо автотестов: прогнал ключевые сценарии через Postman (создание, пересечения, рабочие часы, отмена автором/чужим токеном).
- Перед коммитом всегда читаю diff глазами: контроллер, сервис, валидацию, enum, тесты и т.д.

**Не доверили ИИ:**

- Миграции — агенту запрещено их запускать (только правки файлов при необходимости, apply — вручную).
- Коммиты — только сам, после ручного просмотра изменений.
- Финальную приёмку поведения API — не по «агент сказал, что готово», а по тестам + Postman.
