# Ревью `BookingController`

Разбор `app/Http/Controllers/BookingController.php` и связанного поведения API. Серьёзность: **critical** / **major** / **minor**.

По ТЗ API требует `Authorization: Bearer <токен>`. Идентичность пользователя задаётся Sanctum (`personal_access_tokens` → `tokenable`), а не полями тела запроса. Нарушения этого контракта ниже отмечены как ошибки **авторизации**.

---

## `store` — создание брони

### 1. SQL-инъекция в проверке пересечений — **critical**

```php
DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");
```

Значения из запроса подставляются в SQL строкой. Можно сломать запрос или выполнить произвольный SQL.

**Как исправить:** query builder / Eloquent с биндингами (`where`, `whereColumn`) или `DB::select` с плейсхолдерами `?` / named bindings. Никакой интерполяции пользовательского ввода в SQL.

### 2. Авторизация: автор брони не берётся из Bearer-токена — **critical**

Маршрут защищён `auth:sanctum`, токен однозначно определяет пользователя (`$request->user()`). Тем не менее `user_id` читается из тела и уходит в `Booking::create($request->all())`.

Клиент с валидным токеном Анны может передать `"user_id": 2` и создать бронь от имени Бориса — идентификация через Bearer игнорируется.

**Как исправить:** не принимать `user_id` из запроса; всегда писать `$request->user()->id`.

### 3. Нет серверной валидации входных данных — **critical**

Поля не проверяются через `Validator` / Form Request. Нет гарантий, что есть `room_id`, `title`, `starts_at`, `ends_at`; что комната существует; что `ends_at > starts_at`; что даты парсятся.

`$request->all()` уходит в `Booking::create` — лишние/битые поля либо молча игнорируются (fillable), либо приводят к 500.

**Как исправить:** Form Request или `$request->validate([...])` с правилами на типы, `exists:rooms,id`, формат ISO 8601, `after:starts_at`. Ответы — 422 с понятными ошибками по полям.

### 4. Неверное условие пересечения интервалов — **major**

Текущее условие (`starts_at <= ends_at AND ends_at >= starts_at`) считает пересечением и стыкующиеся интервалы. По ТЗ встречи «впритык» разрешены: `10:00–11:00` и `11:00–12:00` не конфликтуют.

**Как исправить:** строгие границы, например существующая бронь пересекается с новым интервалом, если:

`existing.starts_at < new.ends_at AND existing.ends_at > new.starts_at`.

### 5. Рабочее время считается не по ТЗ — **major**

Проверяется только час начала:

```php
$start = Carbon::parse($request->starts_at);
if ($start->hour < 9 || $start->hour >= 20) { ... }
```

Проблемы:

- не проверяется, что **вся** бронь укладывается в `09:00–20:00` (конец может выйти за 20:00);
- не учитывается часовой пояс офиса комнаты (`offices.timezone`: Москва / Новосибирск) — `Carbon::parse` и `hour` идут в контексте приложения (`UTC` в `config/app.php`);
- клиент шлёт ISO 8601 с любым смещением — нужно привести интервал к локальному времени офиса и уже там проверять границы дня.

**Как исправить:** загрузить комнату с офисом → timezone; сконвертировать `starts_at`/`ends_at` в этот TZ; убедиться, что `start >= 09:00` и `end <= 20:00` того же локального календарного дня (или явно описать политику для броней через полночь — по ТЗ бронь должна целиком укладываться в рабочее окно).

### 6. Нет правил длительности и шага 15 минут — **major**

ТЗ: длительность от 15 минут до 4 часов, шаг 15 минут (границы тоже на :00/:15/:30/:45). В коде этих проверок нет.

**Как исправить:** после парсинга проверить, что минуты/секунды кратны 15 (или что unix-timestamp / Carbon diff кратен 15 минутам), длительность ∈ [15, 240] минут. Ошибки — 422.

### 7. Гонка при параллельных `POST` — **major** (бонус ТЗ)

Схема «сначала SELECT, потом INSERT» без блокировки: два одновременных запроса на один слот оба не видят конфликт и оба создают бронь.

**Как исправить (варианты):**

- транзакция + `lockForUpdate` по комнате / существующим броням;
- exclusion constraint в PostgreSQL на диапазон (`tstzrange` / `tsrange`) по `room_id`;
- уникальный индекс / constraint на непересекающиеся интервалы.

В основной части достаточно корректности при последовательных запросах; гонку лучше закрыть constraint’ом или описать в README.

### 8. Конфликт комнаты отдаётся как 409 с плоским `error` — **minor**

ТЗ просит понятные ошибки валидации (422). `409` с `{'error': '...'}` не единообразен с типичным Laravel 422 (`message` + `errors`).

**Как исправить:** валидировать пересечение как правило валидации (или `ValidationException`) и отдавать 422 с текстом по полю/общему ключу.

### 9. Логирование почти пустое — **minor**

```php
Log::withContext(['booking_id' => $booking->id]);
Log::channel('bookings')->info('Booking created');
```

Канал `bookings` есть, `booking_id` попадёт в context — это работает. Но в сообщении нет `room_id`, пользователя, интервала — по логу сложно разбирать инциденты.

**Как исправить:** писать структурированный payload (`room_id`, `user_id`, `starts_at`, `ends_at`) в сам `info(...)`.

## `destroy` — отмена брони

### 10. Авторизация: отмена без проверки владельца по Bearer-токену — **critical**

```php
Booking::findOrFail($id)->delete();
```

Пользователь уже аутентифицирован через Bearer, но право на удаление не проверяется: любой валидный токен может отменить чужую бронь. ТЗ: отменить может только автор.

**Как исправить:** сравнить `booking.user_id` с `$request->user()->id`; иначе 403 (или 404, если не хотите светить чужие id). Удобнее route model binding + policy/`authorize`.

### 11. Нет type-hint / Form Request для id — **minor**

Сигнатура `destroy($id)` без типов. Не баг, но хуже читаемость и меньше помощи от IDE/анализаторов.

**Как исправить:** `destroy(Request $request, Booking $booking): Response` (или `JsonResponse`).

## `index` — список своих броней

### 12. Нет eager-load / ресурса API — **minor**

Для текущего контракта (только поля брони) N+1 нет. Если позже в ответ добавят комнату/офис — понадобится `with(...)`. Сейчас не баг.

## `today` — брони комнаты «на сегодня»

### 13. «Сегодня» считается в TZ приложения (UTC), а не офиса — **major**

```php
->whereDate('starts_at', today())
```

`today()` = текущая дата в `config('app.timezone')` = `UTC`. Для Москвы (`UTC+3`) и Новосибирска (`UTC+7`) около полуночи по локальному времени список будет чужим днём.

**Как исправить:** взять `$room->office->timezone`, вычислить «сегодня» в этом поясе и фильтровать интервал `[startOfDay, endOfDay]` в UTC/хранении БД (или `whereBetween` по сконвертированным границам).

### 14. N+1 по пользователям — **major**

```php
'author' => $b->user->name,
```

На каждую бронь отдельный запрос к `users`.

**Как исправить:** `$room->bookings()->with('user')->...`.

### 15. Формат времени через конкатенацию Carbon — **minor**

`$b->starts_at . ' – ' . $b->ends_at` опирается на `__toString()` / default format. Формат и TZ ответа не зафиксированы; для UI офиса лучше явный `format` / ISO в TZ офиса.
